# CONTEXT.md — ConfCue

Why ConfCue is built the way it is: architecture and the reasoning behind each decision, including the things that turned out differently than planned.

Companion to `README.md` (how to run and operate it) and `ROADMAP.md` (what's done, what's missing, what's next).

## Project overview
ConfCue — a lightweight web system for a small conference. Attendees scan a QR code during a talk to submit questions. Questions are stored and periodically clustered/summarized by a locally running LLM, then shown on a live moderator dashboard.

## Constraints
- Small conference scale — tens to a few hundred attendees, low request volume (a question every few seconds at peak)
- Venue WiFi is not reliable and cannot be depended on
- Host machine is a Linux station, accessed remotely by the developer
- Summarization/clustering runs on a locally hosted LLM — no external LLM API calls

## Environment status (already in place on the host)
- Tailscale account/tailnet — already set up
- Ollama — already installed, four models pulled (`ollama list`): `mistral-small3.2:24b` (15GB), `gemma4:31b` (19GB), `qwen3.8:27b` (17GB), `llama3.2-vision:11b` (7.8GB, vision — not used here)
- Repo — live on GitHub: `git@github.com:Jaaaaabin/conf-cue.git`

## LLM summarization
- Model in use: **`mistral-small3.2:24b`** (`backend/llm.py`) — picked as the smallest of the three text models pulled; response times observed 0.5–6s for small question sets, acceptable for a 45s background refresh cycle.
- Ollama-calling code pattern reused from `/home/wu/dev/llm-local-runner/REUSE.md` (`call_local_model` / `list_installed_models`), stripped to the minimal copy-paste version since no benchmarking/metrics are needed here.
- `/summary` no longer calls the LLM per-request (dashboard polls it every 4s — hammering Ollama that often would be wasteful and slow). Instead a background asyncio task (`_refresh_summary_loop` in `backend/main.py`) reclusters/summarizes every 45s, offloaded via `asyncio.to_thread` so the blocking Ollama call doesn't stall the event loop, and caches the result. `/summary` just serves the cache. On an LLM call failure, the loop keeps serving the last known good summary rather than erroring.
- Prompt (`llm.build_summary_prompt`) explicitly demands plain prose, no markdown — the dashboard renders the result into a single `<p>`, so bullet points/bold text from the model would show up as literal asterisks otherwise. Manually validated against both a 5-question set with two duplicate clusters (slides, recording) and a single-question case before wiring it in.

## Per-question AI answers ("ConfCue ✦")
- Attendees see a draft answer to their own question on the "My Questions" tab, labeled **ConfCue ✦** (visually distinct — indigo accent, left border — not the ticket-stub red) so it reads clearly as a bot, not a human/official response.
- The model has no real knowledge of this specific event (no slides, no transcript, no venue facts beyond `schedule.csv`) — the prompt (`llm.build_answer_prompt`) explicitly instructs it to say so and redirect to the schedule/contact page/moderator rather than invent specifics for event-bound questions (venue logistics, exact times). Validated manually: correctly declined to guess a WiFi password or recording status, but gave a genuinely useful answer to a general technical question.
- `build_answer_prompt`/`answer_question` take an optional `context: str` parameter — originally a hook for later, now wired up: **Paper RAG is implemented**, see "Paper RAG & figures" below. `call_local_model` also takes an optional `options` dict; `answer_question` passes a generous `num_ctx` (8192) whenever `context` is non-empty, since Ollama's default context window can silently truncate a RAG-enriched prompt otherwise.
- Answered via a second background loop (`_answer_questions_loop`, `backend/main.py`), every 20s, separate from the 45s summary loop since they're different concerns (per-question vs. aggregate). Answers are persisted to the DB (`questions.answer`, `questions.answered_at` — added via a guarded `ALTER TABLE` so the existing dev DB upgrades in place), so they survive restarts and appear identically to every device that asked that question, not just localStorage.
- The My Questions page fetches `/questions` and merges in fresh data (including the answer) rather than only reading the local snapshot, and polls every 5s — so an answer appears without a manual refresh.

## Paper RAG & figures
Two features from `ROADMAP.md`'s feature backlog, both built: ConfCue ✦ answers are now grounded in the actual conference papers when they're indexed, and attendees see the paper's own figures during that talk. The original design brainstorm diverged in several places once real PDFs were tested against; the measured sizing evidence that still justifies future decisions is kept in `ROADMAP.md`.

**The defining constraint driving this design**: paper PDFs, DOIs, and even the schedule itself arrive incrementally and can change right up to the event — nothing may assume a fixed paper count, a DOI being known in advance, or a session's date/time staying put. Every piece below degrades gracefully per-paper/per-session rather than erroring.

### Stable IDs, decoupled from data that can shift
- **`paper_id`** — real conference papers get arbitrary numeric submission IDs (e.g. `123`, `136`...) from the paper management system, unrelated to schedule order. The test/mimic schedule uses `001`–`005`. This is the filename key for everything paper-related: `data/papers/<paper_id>.pdf`, `data/paper_index/<paper_id>.{npz,json}`, `frontend/papers/<paper_id>/`.
- **`session_key`** — a column in `schedule.csv` (`s001`, `s002`... one per row, in schedule order), used everywhere (chat scoping, the "Now" banner, RAG/figures matching, the moderator dashboard's chat groups). Stable if a talk's slot time moves later; `paper_id` and `session_key` are intentionally independent numbering spaces, since a real paper's submission ID has no relationship to when it's scheduled.
- **`frontend/schedule.csv`** is the single hand-maintained source for both scheduling *and* the paper link — no separate `papers.json` anymore. Columns: `session_key,date,time,session_shortname,session_fullname,presenter,paper_id,doi`. `paper_id`/`doi`/`presenter` are blank for non-paper rows (breaks, registration, opening/closing) and filled in whenever known — a paper can get a `paper_id` before it has a PDF or a DOI. `session_shortname` exists because a full academic paper title doesn't fit in a single-line UI element (the "Now" banner, the chat-sheet header, a dashboard group chip) — `session_fullname` is for places that want the real title (the schedule page, citations).
- **`frontend/sessions.json`** is generated from `schedule.csv` by `scripts/build_sessions_index.py` (CSV headers are exactly the JSON keys, so the conversion is close to mechanical) and is what the frontend actually fetches — `index.html`, `schedule.html`, and `dashboard.html` no longer parse CSV in the browser at all. This closes a real latent bug: `nav.js`'s old `parseCsv` was a naive `line.split(",")` with no quote support, so a comma inside a paper title would have silently shifted every column after it (`doi`, `session_key`) — Python's `csv` module (used once, offline, in the build script) handles quoting correctly. Gitignored, like `frontend/papers/index.json` — a build artifact, not something to hand-edit or commit.
- `backend/papers.py` is the shared, dependency-free (no `fastembed`/`pymupdf`) module all of this reads through: `read_schedule()`, `read_papers()` (now derives the old `{paper_id, session_key, title, doi}` shape from `schedule.csv` rows that have a `paper_id`, so `extract_figures.py`/`build_paper_index.py`/`fetch_papers.py` needed zero changes), `session_key(row)`, `doi_for_session_key(key)`.

### PDF sourcing
`data/papers/<paper_id>.pdf` (gitignored, host-only) is the only thing that needs to exist for indexing to work. `scripts/fetch_papers.py` attempts a best-effort automated fetch via DOI content-negotiation, verified by sniffing for the `%PDF-` magic bytes (never trusting `Content-Type`) — but this is a convenience, not a reliable path: DOI resolution is designed for bibliographic metadata, not full text, and almost always 302s to a publisher landing page. **Confirmed empirically**: 0/5 of the real conference DOIs auto-fetched successfully. Manual drop-in is the reliable primary path, not a fallback.

### Paper figures (`scripts/extract_figures.py`)
**Built. Diverged significantly from the original design** after testing against real papers surfaced two real bugs:
- **Bug found**: a naive size-threshold filter on raw embedded images (`page.get_images()`) let through a figure that was tiled across 12 separate embedded XObjects — each a small mosaic cell on the page but with high *native* pixel resolution, so a resolution-based filter couldn't tell it apart from 12 real figures. One paper produced 41 "figures" before this was caught.
- **Bug found**: some real papers use `Separation` (spot-color) colorspaces that crash a naive PNG save; a component-count heuristic (`n - alpha >= 4`, meant to catch CMYK) missed it since Separation also reports `n=1`, same as grayscale.
- **Fix — a different algorithm, not a patched filter**: instead of extracting individual embedded images, the script renders the *page region* near each "Figure N"/"Fig. N" caption as one clipped screenshot (`page.get_pixmap(clip=rect)`). This sidesteps both bugs at once (a page render is always RGB, and doesn't care how many XObjects compose the artwork), and — bonus — captures vector-drawn figures for free, which raw image extraction structurally never could (the original design flagged this as a known gap; it's no longer one).
- Region bounds: horizontally, the caption's own x-range (± a small margin) — this naturally respects multi-column layouts without needing explicit column detection, since a caption is always set to its own column's width. Vertically, from the caption's top upward to the nearest block (in the same column) that ends above it, capped at 380pt as a safety limit.
- A caption match is required for a region to be captured at all, not optional metadata — this is what filters out header/footer logos.
- Output: `frontend/papers/<paper_id>/fig-NN.png` + `figures.json` (number, caption, page), plus one aggregate `frontend/papers/index.json` keyed by `session_key` → `{paper_id, figures}`. Since `frontend/` is already `StaticFiles`-mounted, serving is free. `frontend/papers/` is gitignored (same copyright reasoning as the raw sponsor/partner media kits under `icon_archive/temp/` — bulk-extracted third-party content with no redistribution clearance — the copyright caveat in `ROADMAP.md` still applies before any of this goes live publicly). Unlike `icon_archive/`, though, `frontend/papers/` is meant to be served — the figures are the whole point of the feature — so it deliberately stays under `frontend/`, just uncommitted.
- Frontend: `index.html` fetches the manifest once, looks itself up by `currentSessionKey()` (no DOI needed client-side at all), and shows a thumbnail strip near the "Now" banner — reusing the exact `<a target="_blank"><img></a>` pattern chat images already use, not a new component.
- **Incremental**: a paper whose `figures.json` is already newer than its PDF is skipped on rerun, not reprocessed. `--force` rebuilds everything (e.g. after changing the extraction logic itself).
- **Known gap, not built**: figure captions are not fed into the RAG index — the two pipelines are disconnected. A question like *"what's the first figure about"* won't be answered well even with correct session routing, since RAG only retrieves body-text chunks. Would need each caption indexed as its own small searchable chunk to fix.

### Paper RAG (`scripts/build_paper_index.py`, `backend/rag.py`)
**Built. Two deliberate departures from the original design**, both because the real paper set isn't known/fixed yet — not oversights:
- **Chunking is fixed-window over words (~450 words / 68-word overlap, the ~0.75 words-per-token approximation for the ~600-token/15%-overlap target), not section-aware.** The original design proposed detecting Abstract/Method/Results boundaries; that's a formatting heuristic that would guess wrong unpredictably across publishers not seen yet, and a wrong guess produces *worse* chunks than simple windowing. Citations use page numbers only (each chunk tracks its originating page range), not section labels, for the same reason.
- **PDF sourcing is manual-primary with best-effort auto-fetch**, not "fetch each PDF via its DOI" as a reliable step (see "PDF sourcing" above) — DOI→PDF isn't automatable across mixed publishers in practice, confirmed empirically at 0/5.
- Embedding: `fastembed`, `BAAI/bge-small-en-v1.5`, 384-dim, loaded once (lazily, on first real use — not at import time, not per-question). Vectors explicitly L2-normalized before saving regardless of whether the embedder's own output already is, so a plain dot product at query time is guaranteed to equal cosine similarity.
- No vector database — same reasoning originally worked out (a NumPy dot product over an in-memory array beats a network hop at this scale), still holds — the measured numbers are in `ROADMAP.md`.
- `backend/rag.py`'s `retrieve(session_key, question_text)` is the one entry point, called from `_answer_questions_loop` in `backend/main.py` right before `answer_question`. **Every failure mode — no session_key, session has no paper, paper has no PDF yet, paper has no index yet, or a retrieval error — returns `("", None)` and falls through to exactly today's plain-answer behavior.** This graceful degradation is the actual point: partial progress indexing the real ~50-paper lineup should never break a question.
- Citation anchors to the single top-ranked retrieved chunk's page range, not a span across all k retrieved chunks — caught via manual testing (an early version cited "pp. 1–9" across the whole retrieved set when the actual answer came from one page). Omits the DOI link entirely (page number only) when a paper's DOI isn't assigned yet.
- `QuestionIn` carries an optional `session_key` (the *ask-time* session, mirroring `MessageIn`'s field but kept `None` rather than defaulted to `"lobby"` — there's no real value to invent). Stored on the `questions` row (`session_key`, `citation` columns, guarded-`ALTER TABLE`) and read back at answer time, up to 20s later — deliberately the session at ask-time, not whatever's "current" when the loop happens to run, so a question about a talk that's ending doesn't get answered from the next talk's paper.
- **Incremental**, same shape as figures: a paper whose index is already newer than its PDF is skipped; `--force` rebuilds. The embedding model is loaded lazily, only once there's actually something to embed, so a no-op incremental run costs no model-load time.
- Verified end-to-end against all 5 real conference papers (not just synthetic test data): real grounded answers, accurate page citations, correct DOI links.

## Page structure
- `/` is the **ask page and nothing else** — the two-tab (Ask / My Questions) switcher was removed so the form is the single thing the page is for. "Ask your question." is the hero headline; the now-banner and reaction stamps sit above it as ambient context, and a quiet footnote link points to the previous questions.
- Previous questions moved to their own page, `/myquestions.html`, reached from the fold-out nav or that footnote — taking the AI answers and classification chips with them.
- Fold-out nav is identical on all six attendee pages: **Chat · Schedule · Sponsors & Partners · Venues · Contact · My Questions** — the first item is labeled "Chat" but links to `/`, the ask page — each marking itself current. (The moderator dashboard deliberately has no nav — it is a projector surface, not something anyone browses.)

## Spacing scale & narrow-phone behaviour
- Layout spacing runs off four `:root` tokens rather than per-rule literals — `--gutter` (page side padding, on every `.stage`), `--section-gap` (`.board-feed` rhythm), `--card-pad` (schedule accordion + session card), `--stub-pad` (ask card). Same one-control-point idea as the pre-existing `--heading-*` vars.
- **Those tokens ramp fluidly with `clamp()` across a 320px→390px viewport instead of stepping at a breakpoint.** The reason is specific and worth keeping: the narrow-screen problem was never one oversized value, it was *compounding inset* — at 320px a session title sat behind gutter + accordion padding + card padding + two borders, ~61px of chrome per side, leaving under 200px of actual text column. A plain `max-width: 360px` breakpoint fixed 320px but created a **width inversion**: a 360px phone then showed a *wider* text column than a 375px one, because the wider phone fell back to full-size padding. Ramping removes the inversion by construction. Verified across 7 pages × 11 viewports (320→1440): no horizontal overflow, no wrapped section headings, and the text column grows monotonically with viewport width.
- The `@media (max-width: 360px)` block at the end of `style.css` is therefore deliberately small — only genuinely step-shaped changes live there (a tighter `--section-gap`, reduced ask-card *vertical* padding, and the stamp grid below). Anything continuous belongs in the token ramps.
- The 6 reaction stamps can't fit one row at the 44px minimum tap size on a narrow phone, and the default flex wrap left a ragged 4 + 2 that read as a bug. Below 360px they become an explicit 3-wide grid, so the two rows look intentional and every target stays full size.
- **Tap targets**: the address copy / open-in-Maps buttons were 30×30 and the fold-out nav links 38px tall — both under the 44px minimum, and both are primary controls. Now 44px. Deliberately *not* enlarged: inline links inside prose (email addresses, the "previous questions" footnote) and the DOI pill (31px) — these clear the WCAG 2.5.8 AA 24px minimum, and padding the DOI pill to 44px would bloat every session card for a secondary link.
- The venue map embed used to carry a hardcoded inline `width: 75%`, which left only ~200px of usable map on a 320px screen. It is now a `.venue-map` class at full content width.

## Sponsors, Venues & Contact pages
- `/sponsors.html` — three sponsor tiers (Platinum / Gold / Other, `.sponsor-tier--*` in `style.css`) share one markup shape (`sponsor-tier__head` / `__label` / `__rule` / `__body` + `.sponsor-logo`) but are deliberately styled with decreasing decoration so the rank reads at a glance without reading any text — Platinum has the most going on, Other the least:
  - **Platinum**: near-black card (`--tier-black*`, cool graphite-blue on purpose — literal platinum's own metallic feel, not gold's warmth), two large low-contrast `conic-gradient` facet clusters mirrored across the diagonal, a top radial "key light" glow, a `tier-diamond` mark built from four `clip-path` triangles (no SVG/image), and an infinite `tier-sheen` animation sweeping the card. **Gotcha**: `translateX()` in a `@keyframes` on a pseudo-element resolves against *that element's own width*, not its container's — the sheen element is 26% of the card wide, so reaching the card's actual edges needs percentages like `-130%`/`415%`, not `-100%`/`100%`. The "PLATINUM" label and diamond body both use a `--plat-100→gold-200` progressive gradient (`background-clip: text`), so the label itself visually shifts from platinum to gold.
  - **Gold**: shallow champagne gradient, a bright corner highlight, and two inline `<svg>` flowing wave-line paths (`sponsor-tier__waves` in the HTML, not CSS-only) with a faded-both-ends `linearGradient` stroke — kept in the card's top/bottom margins so they never cross the sponsor logo.
  - **Other**: same shared shape, brushed-silver gradient, no glow/curve/animation at all — intentionally the plainest of the three.
  - Below the tiers, a **Partners** section — 9 logos in a fixed **3×3 CSS grid** (`.org-logo-list--grid`), not a single row: a single `flex-wrap: nowrap` row got too cramped to stay legible on a phone once the count passed ~7. Equal height across the grid is handled by the CSS replaced-element sizing algorithm itself (`height: 100%` + `width: auto` on each image) rather than hardcoded per-logo values — a logo whose aspect ratio would otherwise make it wider than its own column (Oskar von Miller Forum's plain-text wordmark, ~8:1) automatically renders shorter instead of overlapping its neighbors. One logo (Georg Nemetschek Institute) is deliberately enlarged past 100% via a `--120` modifier class, intentionally spilling a little into the row gap.
- `/venues.html` — conference venue (Oskar von Miller Forum) and conference dinner (Löwenbräukeller) each get an address in a `.terminal-box` with a copy-to-clipboard button and a "open in Google Maps" link; the venue section additionally embeds a Google Maps iframe. Venue floor-plan image and confirmed dinner time are still "coming soon" placeholders.
- **"Organized by"** (`frontend/icon/org/`, 5 logos: TUM, EUnet4DBP, OGC, University of Auckland, DigiB) appears on **every attendee page** (`index.html`, `schedule.html`, `venues.html`, `sponsors.html`, `contact.html`, `myquestions.html`) via byte-identical markup — same `.org-logo-list` component the Partners section started from, but laid out as a single row with `justify-content: space-between` so the 5 logos spread edge-to-edge instead of being sliced into equal-width columns. Deliberately **not** on the moderator dashboard (no nav there either — see "Page structure"). TUM's mark is a solid-filled block (not a floating wordmark like the others) so it reads visually larger at the same box height — scaled to 90% via a modifier class; EUnet4DBP is nudged up to 110% the other way. **Gotcha hit here**: a percentage-based `max-width`/`max-height` override (e.g. `125%`) does not count toward how much space a shrink-to-fit flex item reserves for its neighbors (percentages resolve to `none` for intrinsic-size purposes per the CSS sizing spec) — the enlarged item silently overlapped its neighbor until the override was switched to an absolute `rem` height instead (`.org-logo-list__item--110`, `height: 3.3rem`). The 4 gaps between all 5 logos stay equal automatically when a size changes, since `space-between` + `gap` redistributes free space rather than dividing the row into fixed columns — verified via Playwright `bounding_box()` on all 6 pages after the 125%→110% adjustment.
- **Logo file naming**: every logo actually referenced by a page has a `_final` suffix (e.g. `org_2_final.png`, `par_11_final.png`, `spo_gold_1_final.png`) — this is what marks a file as "the processed, in-use asset," as opposed to a raw/original source. Partner logo filenames additionally encode their current grid position (`par_11`…`par_33` = row·col, 1-indexed) rather than upload order — **tradeoff**: reordering the 3×3 grid later requires renaming files to keep the position encoding meaningful, it isn't automatic.
- **Logo pre-processing**: each `_final` file is cropped to its visual content's bounding box (detected via alpha transparency, or a corner-color diff for opaque source JPGs) plus a small proportional padding margin — normalizes wildly inconsistent embedded whitespace across logos supplied by different organizations (one source file was ~76% empty margin before cropping). DigiB's source mark is white-on-transparent and would vanish against the page's light background; its `_final` file has every white pixel recolored to a fixed navy (`#001f3d`), alpha channel untouched — the original white version is kept as `icon_archive/org/save_org_5.png` for reference, not deleted.
- **Section-title typography**: every section heading across all seven pages (`.board-feed__heading` and `.board-summary__heading` — "Sponsors," "Partners," "Organized by," "Questions," "Chat," etc.) shares one `--heading-size` variable and now one `--font-heading` variable too, so a single edit in `style.css` stays consistent everywhere by construction. Font changed from `--font-mono` to **Quicksand** (a rounded, soft-feeling Google Font, weights 500/600/700, loaded via a `<link>` in every page's `<head>`, falling back to `ui-rounded`/`SF Pro Rounded`/the body sans-serif if the network fetch fails) and `--heading-size` raised from `0.72rem` to `1rem` — two steps up the size scale already in use elsewhere in the file (`0.72 → 0.78/0.85 → 0.92/1rem`). The dashboard's foldable group labels (`.feed-group__summary`) already shared the heading size/tracking vars, so they take `--font-heading` too — before this change they were pixel-identical to the section titles, and leaving them on mono would have split a pair that used to match.
- Two follow-on corrections once the larger size was live: `--heading-tracking` came down from `0.14em` to `0.07em`, because an all-caps tracked label is the first thing to wrap on a phone and "Conference Dinner Information" was wrapping even at 390px; and `--heading-size` became a `clamp()` ramp (`0.92rem` at 320px → `1rem` at 390px) for the same reason, on the same track as the other spacing tokens. Verified via Playwright across 7 pages × 11 viewports (320→1440): `Quicksand` resolves as the live computed `font-family` on every heading, and no heading wraps or overflows at any width.
- **Raw/unused source assets do not live under `frontend/`.** They're kept in **`icon_archive/`** at the repo root (`icon_archive/org/`, `icon_archive/par/`, `icon_archive/temp/`), gitignored only for the `temp/` media-kit portion. This is a deliberate fix, not just tidiness: `frontend/` is mounted wholesale via `StaticFiles` (`backend/main.py`), so anything placed under it — including a prior `frontend/icon/temp/` that was gitignored — is still publicly servable over the live Funnel URL regardless of git status. Confirmed empirically: a file under the old `frontend/icon/temp/` path returned `200` before the move and `404` after. **The one thing to remember going forward: never add a new "raw"/"unused"/"reference" asset folder under `frontend/` — it belongs in `icon_archive/` (or `data/`, also gitignored and unmounted) instead**, or it's public the moment it's saved to disk.

## Question classification
- Two-stage submit. Stage 1 is a single **Submit** button; tapping it doesn't send anything — it splits itself into three side-by-side buttons (**Just Curious** / **Check Paper** / **To Moderator**, left→center→right). Stage 2: tapping one of those is what actually sends the question, with that category attached (`POST /questions` accepts an optional `category` alongside `text`). After a successful send the form collapses back to the single Submit button, ready for the next question.
- Stage 1 is the form's `submit` event, so the input's native `required` validation gates it — an empty question never reaches the split. The three category buttons are `type="button"` (not submit) so pressing Enter in the input can only ever trigger stage 1, never accidentally fire a category.
- The asker can still change their mind afterward: "My Questions" shows the same three options as secondary chips per card, pre-selected to whatever was chosen at submission, single-select (picking a different one replaces it; tapping the active one again clears it). Backend: `POST /questions/{id}/category`, same `Category` literal type shared with the create-time field.
- Stored in `questions.category` (added via the same guarded-`ALTER TABLE` pattern as `answer`).
- The moderator dashboard shows the chosen category as a small pill tag on each question card, so a moderator can triage at a glance (e.g. skip past "Just Curious" ones, prioritize "To Moderator").

## Rate limiting & moderator delete
Built, closing what was previously the most exposed surface on a public Funnel URL (anonymous, unthrottled `POST` endpoints, no way to remove anything).

- **Rate limiting** (`backend/ratelimit.py`) — in-memory sliding-window log, per client IP, no new dependency (no slowapi/redis — unjustified at this scale, single process, no `--workers`). Limits live in `RATE_LIMITS` in `backend/main.py`: questions 1/10s, category changes 1/3s, chat messages 1/3s, image uploads 1/15s, reactions 20/60s (deliberately generous — reactions are an intentional rapid-tap "applause meter" by product decision, not abuse). A 429 needed **no frontend changes** — both existing client error-handling patterns (the question form's generic failure message, the reaction tap's fully-optimistic-and-silently-reconciled pattern) already degrade gracefully.
  - Client IP comes from `X-Forwarded-For`, falling back to `request.client.host`. **This is safe only because uvicorn binds `127.0.0.1`, not `0.0.0.0`** — nothing but the Funnel proxy (or a process already on the host) can reach the port to set that header. If the bind host is ever changed, this becomes spoofable.
  - **Not yet verified from two real, differently-networked attendee devices through the actual Funnel URL** — flagged as a hard pre-event gate, not optional. If `X-Forwarded-For` isn't actually coming through correctly for some Funnel configuration, every attendee falls back to the same `127.0.0.1` bucket and the whole limiter visibly breaks the app (one person's question blocks everyone else's).
- **Moderator delete** — `DELETE /questions/{id}` and `DELETE /messages/{id}`, gated by a single shared secret (`MODERATOR_KEY` env var, not a login/session system) compared with `secrets.compare_digest`. **Fails closed**: if the env var isn't set at all, every delete is rejected, never silently unprotected. Dashboard viewing itself stays exactly as open as before — only the delete action is gated, and the key prompt (`window.prompt`, saved to that browser's `localStorage`) only fires lazily on the first delete click, not on page load.
  - Dashboard UI exists for both questions and chat (`dashboard.html`, a Delete button per feed card, wired via event delegation on each list container since both feeds are fully rebuilt every poll — a listener on the button itself would be destroyed on the next poll). Both delete flows share the same stored moderator key.
  - **Chat moderation panel**: `GET /messages/recent` (new, ungated — same "viewing open, deleting gated" split as questions) returns the most recent messages across *every* session at once, newest-first, so the moderator doesn't need to pick a session to find a bad message. Deletes go through the existing gated `DELETE /messages/{id}`. The delete button here is a real 44×44px tap target (`.chat-mod-delete`), not the small text-link used for questions — this panel is meant to be usable from a moderator's own phone while roaming, not just the projector board, and the board's base CSS is already mobile-first (the `@media (min-width: 900px)` rules only *add* the wider projector layout).
  - Both the Questions feed (grouped by category) and this Chat panel (grouped by session) are foldable — a `<details>` per group, fold state kept in `localStorage` per group key so it survives the 4s poll rebuild. "Just Curious" starts folded by default (mirrors the documented triage habit of skipping past it), chat groups show the session's real `session_shortname` (via `frontend/sessions.json`) instead of the raw `session_key`, falling back to the raw key for `"lobby"` or anything not in the schedule. Unrecognized categories/sessions still get their own group rather than silently vanishing.
  - Deleting a message with an `image_url` does not delete the underlying file in `data/uploads/` — same tolerance for this class of gap as `reset_data.py`'s own row-ID-not-reset behavior.

## App supervision — systemd
Built, closing the other half of what was previously the biggest reliability gap (a manually-started `uv run uvicorn`, dying on any crash or on the developer's SSH session ending). Full day-to-day operating instructions (checking status, making a change, pausing, rotating the moderator key, the pre-event checklist) live in **`README.md`** Part 3 — this section is the "why," that one's the "how."

- System-scope unit (`/etc/systemd/system/conf-cue.service`), not user-scope: this host has `Linger=no` (confirmed via `loginctl`), so a user-scope unit would silently stop the moment the developer's SSH session ends — exactly the failure being fixed. `User=wu`/`Restart=always`/`RestartSec=3`, `EnvironmentFile=/etc/conf-cue.env` (root-owned, mode 600 — keeps `MODERATOR_KEY` out of the world-readable unit file).
- `tailscaled` itself needed no new supervision — already a proper enabled systemd system service; Funnel's serve config persists in its own state across daemon restarts.
- `--reload` is still on in the unit (active development ongoing) — an explicit pre-event checklist item in `README.md` to turn off, trading "backend edits apply instantly" for "one less moving part" during the live event.
- Verified: `kill -9` on the actual worker process (not just the top-level `uv run` PID) → whole tree restarts within seconds, confirmed via `journalctl`; manually running `uv run uvicorn` now correctly fails with "address already in use" against the systemd-owned process (expected, not a bug to chase).

## Architecture
1. **Attendee's phone** — scans QR code, opens the question form
2. **Backend + database** — receives and stores each submitted question
3. **Local LLM (Ollama)** — clusters and summarizes questions periodically
4. **Moderator dashboard** — live feed for the speaker/host

## Networking — Tailscale Funnel
Chosen approach: since venue WiFi can't be relied on, the Linux host exposes its local service to the public internet over HTTPS via Tailscale Funnel. Attendees connect over their own cellular data — no shared network required, no VPN client on their side.

### Host requirements (Linux station)
- Free Tailscale account, host enrolled in a tailnet
- Tailscale client installed and running (recent version — CLI syntax changed in v1.52)
- HTTPS enabled on the tailnet (auto-prompted the first time Funnel is used)
- `funnel` node attribute granted to the device (auto-granted via interactive CLI setup, or added manually in the admin console on a managed tailnet)
- App must listen on an allowed Funnel port: `443`, `8443`, or `10000`
- Host needs its own outbound internet connection (ethernet, hotspot, or cellular) — Funnel removes DNS/cert/port-forwarding hassle, but the machine still needs a way online
- Host must stay awake and connected for the whole session — Funnel drops if Tailscale disconnects or the machine sleeps

### Attendee requirements
- None — no Tailscale account, no app install, no VPN client
- Just a phone browser and their own data connection
- Scan QR code → opens `https://<device>.<tailnet-name>.ts.net` like any normal website

### Current funnel URL
`https://wu.tailc772b5.ts.net` — proxies to `http://127.0.0.1:8000`. Verified working end-to-end from an off-network phone on cellular data.

Day-to-day Funnel operation — when *not* to run `funnel reset`, the first-time DNS propagation lag, and the pre-event reachability check — is in `README.md` Part 3.

## Tech stack
- **Frontend**: static HTML question form (no framework required)
- **Backend**: Python, FastAPI + uvicorn — single `POST /questions` endpoint to start
- **Environment**: `uv` for local Python setup and dependency management. Docker was never used — resilience ended up solved with a systemd unit instead (see "App supervision" above), which needed no container at all
- **Storage**: SQLite
- **Live updates**: polling every 3–5s (simpler than websockets at this scale, and sufficient)
- **LLM processing**: Ollama running locally on the host, invoked periodically (every 30–60s) to cluster/dedupe incoming questions and surface top/summarized ones
- **Paper RAG/figures**: `fastembed` (local ONNX embedder — Ollama itself rejects embeddings on this host, confirmed) and `pymupdf` (PDF text/page-region extraction); `httpx` for the best-effort PDF auto-fetch

## Repo layout & reproducibility
`README.md` is the entry point for a fresh clone (requirements, run commands, the optional paper pipeline). This section is only the reasoning behind how the repo is arranged.

- **The app is not a Python package.** `pyproject.toml` declares `[tool.uv] package = false` and has no `[build-system]`, so `uv sync` installs dependencies and stops — no build step, no editable install. It is run as `uvicorn backend.main:app`, never imported as a library. The `src/conf_cue/` tree `uv init` originally scaffolded (a `main()` printing "Hello from conf-cue!") was dead the whole time and has been deleted.
- **What's committed vs. generated.** `.gitignore` is grouped by *why* a path is excluded rather than as a flat list, because that distinction is what matters when cloning: runtime state (`data/*.db`, uploads), generated artifacts (`frontend/sessions.json`, `frontend/papers/`, `data/paper_index/`), fetched sources (`data/papers/` PDFs), and the 105 MB of raw media kits in `icon_archive/temp/`. Every generated path names the script that rebuilds it, so nothing ignored is unrecoverable.
- **The one non-obvious first-run step** is `scripts/build_sessions_index.py`. `frontend/sessions.json` is generated *and* gitignored *and* fetched by every page, so a fresh clone that skips it gets an empty schedule, no "Now" banner and broken chat session routing — with no error explaining why.
- **`data/.gitkeep` is tracked** so the directory survives a clone; every other runtime directory is created by `mkdir(parents=True, exist_ok=True)` in the code that needs it.
- **Only one environment variable exists** (`MODERATOR_KEY`), and the app reads the process environment directly — there is no `python-dotenv`. `.env.example` says so, rather than implying a `.env` gets auto-loaded. Model names are constants in `backend/llm.py` / `backend/rag.py`, not env-configurable, deliberately: they're pinned to what's actually pulled on this host.
- **Verified, not assumed**: the exact file set git would carry was copied to a clean directory and run there — `uv sync`, the index build, then the server, with all seven pages and the API returning 200 and the SQLite DB created on first start. The only 404 is `/papers/index.json` before any paper is processed, which `index.html` catches by design and treats as "no figures to show."

## Manual data reset
`scripts/reset_data.py` wipes every question (answers + categories), reaction, chat message, and uploaded chat image. Not a routine thing — it's for the testing phase, or a major-issue reset mid-event, not a regular reset. Host-only by design — run it directly on the machine (`uv run python scripts/reset_data.py`, or `--yes` to skip the confirmation prompt); there is deliberately no HTTP endpoint for this, since the app is reachable by anyone with the public Funnel URL and an exposed "wipe everything" route would be the single biggest risk in the app. Row IDs are **not** reset (autoincrement keeps climbing) — a mid-event reset can happen while the server still has live traffic, and reusing IDs risks an in-flight AI answer landing on the wrong question, or an attendee's local cache merging with an unrelated new item that reused their old ID. A running server picks up the empty state on its own (reactions/chat immediately, the summary panel within its normal 45s refresh) — no restart needed.

Does **not** touch paper data — `data/papers/`, `data/paper_index/`, `frontend/papers/`, and `frontend/schedule.csv`/`sessions.json` are all untouched by a reset, since they're not per-attendee content, they're the conference's own reference material.

## Reaction stamps
- Six one-tap stamps — 🔥 ❤️ 👏 🤔 😄 🎉 — sit under the "Now:" banner on the attendee page (they react to the talk playing *now*), with live counts. The moderator board shows the same six as pill chips inside the "On the floor" panel.
- **Counts are a rolling 5-minute window, not a running total.** A cumulative counter tells you nothing about the current moment — by hour three of a conference it's just a monotonic number. `reactions` is an append-only table (`emoji`, `created_at`, indexed on `created_at`); `db.reaction_counts(window_seconds)` returns both `recent` (windowed — what the UI shows) and `total` (all-time, kept for the record). Same reasoning applies to the pace dial in `ROADMAP.md`.
- Taps are optimistic client-side (the poll is 5s away, a tap must feel instant), then reconciled from the POST response and the next poll. Repeat taps are allowed and intended — it's an applause meter, not a one-vote-per-person poll. There is **no per-person rate limiting**; abuse prevention is not implemented.
- The leading emoji is highlighted on both surfaces. `POST /reactions` validates against the six via a Pydantic `Literal` (anything else → 422); both endpoints return an identical normalized payload including every emoji, so the client always renders a stable row.
- Payload is ~200 bytes, negligible next to the `/questions` list (see "Known gaps") — which is why this got its own endpoint rather than being folded into an existing poll.

## Public session chat
- Floating message button, bottom-right of the Questions page; tapping it opens the thread with a composer. Closes via the ✕ or Escape — plus clicking the backdrop on desktop. On phones the full-screen sheet covers the scrim completely, so the backdrop is unreachable by definition; it is not rendered below 640px rather than left as a dead overlay.
- **Full screen on phones**, sized with `100dvh` (falling back to `100vh`). A partial-height bottom sheet gets squeezed when the on-screen keyboard opens; `dvh` shrinks with the keyboard so the composer stays put instead of being pushed off-screen. Header is pinned top, composer pinned bottom, messages scroll between (`min-height: 0` on the list is what makes that scroll work inside a fixed-height flex column). Bottom padding respects `env(safe-area-inset-bottom)` for the iPhone home indicator. At ≥640px there is no keyboard overlay, so it stays a compact right-anchored panel.
- **The composer owns the bottom third** (`33dvh`) — a multi-line `<textarea>` with the Send button stacked beneath it, so there is real room to type and review before sending. Enter inserts a newline; **Ctrl/Cmd+Enter sends**, as does the button. Sent messages render with `white-space: pre-wrap` so typed line breaks survive display instead of collapsing. The desktop panel opts out of the 33% rule (it would swallow the short panel) and uses a fixed minimum text-area height instead.
- **Scoped per session.** Each talk gets its own thread, so the conversation stays about what's on stage and any single fetch stays small; outside session hours it falls back to a `"lobby"` thread. The session is resolved with the same rule the "Now:" banner uses, so both agree.
- Messages are **public and anonymous** — no names, no accounts. The sheet says so above the composer rather than leaving it implied. Your own messages are marked "you" and right-aligned, matched by message IDs kept in `localStorage` (`confcue_my_messages`); that marking is per-device cosmetic only, and the server does not know who wrote what.
- The client resolves and sends `session_key` (it owns `schedule.csv` parsing). That's trivially spoofable — acceptable for an anonymous public chat at this scale, but it means thread scoping is **not** a security boundary.
- Polling is deliberately asymmetric to keep bandwidth sane: **4s while the sheet is open**, **20s while closed** (only to light the unread badge, which is tracked via a last-seen message id in `localStorage`). Text is capped at 500 chars server-side, blank/whitespace rejected (422), and a fetch of one thread is capped at 200 messages.
- Failed sends put the text back in the input rather than silently dropping it.
- **Images.** An attach button sits beside the composer; attendees can send a photo (a slide, a diagram, a whiteboard) with or without a caption. Tapping an image opens the full size.
  - **Resized in the browser before upload** (longest edge 1600px, JPEG q0.85). Attendees are on cellular — uploading an untouched 8 MB phone photo would be slow and expensive for them. Measured: 2.4 MB → ~1.1 MB, 4032×3024 → 1600×1200.
  - **The canvas re-encode also strips all EXIF, including GPS.** Phones embed coordinates in photos, and this is a *public* URL; publishing attendee locations would be a real privacy leak. Verified with a real EXIF parser: source had Munich coordinates, stored file has no EXIF block at all.
  - Uploads land in `data/uploads/` (gitignored, **not** in `frontend/` — it is user content, not source) and are served by a `/uploads` mount registered *before* the catch-all frontend mount.
  - Server-side checks: **magic-byte sniffing**, not the client's content-type; **SVG deliberately rejected** (script-execution vector); 6 MB cap; server-generated filenames (a client filename is never trusted); and `image_url` on a message must be a `/uploads/` path this server minted, so a message cannot embed a remote or `javascript:` URL that every attendee's browser would then load.
  - **An image may be sent with no caption at all.** The text field is optional when an image is attached (and vice versa); an empty caption line is hidden rather than left as a blank gap.
  - **EXIF orientation is baked into the pixels** via `createImageBitmap(file, {imageOrientation: "from-image"})`. Phones store a portrait photo as *landscape* pixels plus a rotate flag — and since the re-encode strips EXIF, that flag must be applied first or every portrait photo arrives on its side. Verified: 4032×3024-on-disk with orientation 6 → stored 1200×1600 upright.

### Composer layout rules (learned the hard way)
The chat column is fragile in ways that only show up on a real phone, so these are deliberate:
- `.chat-list` uses **`flex: 1 1 0`**, not `1 1 auto`. With `auto` a long thread uses its *content height* as the flex basis, overflowing the column and squeezing the composer down (measured: 33% → 27%).
- `.chat-form` carries `height: 33dvh` **plus `min-height: min-content`** — it shrinks on a short keyboard-open viewport so Send is never pushed off, but squeezing it past its content made it spill over the notice line and cover the Send button.
- The **row** owns the composer height, not the textarea: an explicit `height` on a flex item defeats shrinking, which is what pushed Send off small screens in the first place.
- `.chat-sheet__header` must **not** shrink (`flex: 0 0 auto`) or the close button gets clipped; `.chat-sheet__header > div` needs **`min-width: 0`** or the nowrap session-title line expands it and shoves the close button off the right edge.
- A `max-height: 340px` media query trims header padding and hides the scope line, so a small phone with a large keyboard still fits the composer and Send.
- Verified across 3 photo shapes × 4 viewport heights (664/420/360/300 px), asserting Send is on-screen, non-overlapping, and genuinely hit-testable.
